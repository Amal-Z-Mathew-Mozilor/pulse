## Morning — Railway deployment

Backend was running on my Mac behind ngrok. Sleep the laptop → product goes
offline. The next critical milestone was getting it hosted properly.

### Preparing the backend repo

Created a clean separate Git repo at `Pulse/backend/` and pushed to a new
GitHub repo `pulse-backend`. Made sure `.gitignore` excluded `.env`,
`.pulse_encryption_key`, `.venv/`, and the local `pulse.db` files. Verified
with `git diff --cached --name-only` before committing — no secrets staged.

Added a Procfile defining two process types:

```
web:    uvicorn app.main:app --host 0.0.0.0 --port $PORT
worker: PYTHONPATH=. procrastinate --app=app.worker.app worker
```

The `PYTHONPATH=.` is critical for the worker. Procrastinate's CLI doesn't
add CWD to `sys.path` by default, so without that prefix it can't import
`app.worker.app`. Found this the hard way after the worker crashed with
"Could not load app from app.worker.app" on first deploy.

### The Railway env-var dance

Railway's deploy model: connect a GitHub repo → it auto-builds → asks
nothing about config. Env vars are set per-service via the dashboard.

First crash on web service:
```
psycopg.ProgrammingError: missing "=" after "sqlite+aiosqlite:///./pulse.db"
```

`DATABASE_URL` wasn't set on the web service, so the app fell back to its
default value from `config.py` — the local SQLite URL, which psycopg can't
parse. Pasted the full env block into web service's Variables → it started.

Then the WORKER crashed with the same error. Turns out I'd only set env
vars on web. Realized too late that Railway env vars are **per-service**,
not project-wide by default. Pasted the same block on worker → both online.

> **Lesson**: use Railway's *Shared Variables* (project-level) for anything
> both services need. Same `DATABASE_URL` on both is the rule, not the
> exception.

## The connection-pool drama

Both services online for ~5 minutes. Then both crashed:

```
FATAL: (EMAXCONNSESSION) max clients reached in session mode -
max clients are limited to pool_size: 15
```

Supabase's free-tier *session pooler* (port 5432) caps concurrent client
connections at 15. Between SQLAlchemy + pgvector + procrastinate on web,
plus the worker also opening pools, we were blowing past 15 easily.

But the worker needs `LISTEN/NOTIFY` for procrastinate, which only works
in *session mode*. Transaction mode (port 6543, 200+ connections) doesn't
support LISTEN.

The fix is a **split connection strategy**:

```
                     Free-tier limit     What uses it
─────────────────────────────────────────────────────────────
Transaction pooler   200+                SQLAlchemy queries
   :6543                                 pgvector searches
                                         Most app traffic

Session pooler        15                 Procrastinate (needs LISTEN/NOTIFY)
   :5432
```

Added a new env var `PROCRASTINATE_DATABASE_URL` that points to the session
pooler. Main `DATABASE_URL` now points to transaction pooler. Procrastinate's
PsycopgConnector pool is capped at `max_size=2`, so two services × 2 = 4
connections, well under the 15 limit.

Re-enabled the asyncpg `statement_cache_size=0` workaround in `db.py` since
we're back on transaction-mode pooling. Bumped SQLAlchemy `pool_size` to 15
+ `max_overflow=10` since transaction pooler can handle the load.

### Subtle bug: how procrastinate accepts pool kwargs

The first attempt looked like:

```python
PsycopgConnector(conninfo=..., kwargs={"min_size": 1, "max_size": 2})
```

Crashed immediately on Railway with:
```
invalid connection option "min_size"
```

It was passing `min_size` as a libpq connection parameter rather than to
`psycopg_pool.AsyncConnectionPool`. The correct form is:

```python
PsycopgConnector(conninfo=..., min_size=1, max_size=2)
```

`**kwargs` directly, not wrapped in a `kwargs=` dict. ~3 lines of changes.

## The Vercel → Railway cutover

With Railway green, time to point the frontend at it.

Updated `VITE_API_BASE_URL` on Vercel from the ngrok URL to the Railway URL.
The hardest part was realizing **Vercel doesn't auto-redeploy when env vars
change** — and using the existing build cache would keep the old URL baked
in. Had to:

1. Settings → Environment Variables → update
2. Deployments → ⋯ → Redeploy
3. **Uncheck "Use existing Build Cache"** ← critical
4. Hard-refresh after the build completes (`Cmd+Shift+R`)

Once that worked, login from Vercel hit Railway hit Supabase. End-to-end
in production for the first time. Real milestone.

### CORS regex for preview URLs

But: opening a Vercel preview URL (the `pulse-frontend-j8zoemllp-...vercel.app`
format that's unique per build) hit a CORS error. The Railway backend only
allowed the production URL `pulse-frontend-navy.vercel.app`.

Fix: add `allow_origin_regex` to the CORS middleware matching any URL of the
shape `https://pulse-frontend-[a-z0-9-]+\.vercel\.app`. Now preview and
production both work, but only for *this* project's deployments.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.cors_origins_list,
    allow_origin_regex=r"https://pulse-frontend-[a-z0-9-]+\.vercel\.app",
    ...
)
```

## Anthropic 529 overload — graceful degradation

The chatbot started returning 500s during a busy hour. Logs showed:

```
anthropic.InternalServerError: Error code: 529 — {'type': 'error',
  'error': {'type': 'overloaded_error', 'message': 'Overloaded'}}
```

Anthropic's API was just overloaded. The SDK retries 3 times with backoff
(~10-20s total), then re-raises. The user saw a generic 500, which is
terrible UX for a transient cloud issue.

Wrapped the `/api/ask` endpoint:

```python
try:
    result = await query_agent.run(...)
    return AskResponse(response=result.text, ...)
except (InternalServerError, APIStatusError) as e:
    if isinstance(e, InternalServerError) or e.status_code in (529, 503):
        return AskResponse(
            response="Claude is temporarily overloaded — try again in a minute.",
            tool_calls=[],
        )
    raise
```

Same logic later added to the streaming endpoint. Users now see a friendly
sentence in the chatbot instead of a red error toast.

## The slowness problem

API responses to the frontend were taking **3-15 seconds** even for simple
endpoints like `/api/status`. The dashboard felt molasses-slow when
switching tabs.

Profiled it. `/api/status` is essentially `SELECT label FROM jira_accounts`
+ some in-memory lookups. 3 seconds is wildly wrong.

Three contributing causes:

1. **Pool exhaustion** — `pool_size=3, max_overflow=2` was small. The
   dashboard polls 4 endpoints (status, alerts, jira-projects, agent-runs)
   on intervals between 4 and 10 seconds. With 4 concurrent requests, the
   5th and 6th queued, taking 2+ seconds before even starting.
2. **`pool_pre_ping=True`** — adds a `SELECT 1` round-trip on every checkout.
   Useful against stale connections, but each ping is ~50ms Singapore→Mumbai,
   so it added measurable latency.
3. **Supabase free-tier "nano" compute** — shared CPU. Just slower per query
   than dedicated.

Fixes:
- `pool_size=15, max_overflow=10` (we're on transaction pooler, can afford it)
- `pool_pre_ping=False` (transaction-mode connections are fresh per transaction
  anyway)
- Slowed the frontend polling intervals from 4-10s → 30s. Notification
  freshness suffers slightly, but the dashboard feels normal again.

After: most endpoints under 500ms. Tabs feel instant.

> **Long-term**: move Railway to Singapore region (closer to Supabase
> Mumbai) for sub-50ms inter-service latency. Upgrade Supabase compute
> when scale demands. Both deferred.

## Resend email integration

`RESEND_API_KEY` was unset, so verification + password-reset emails were
logging to Railway stdout instead of actually delivering. Fine for
development. Useless for customers.

Signed up at resend.com (free 3000/month) → created API key → pasted into
Railway. Done in 5 minutes.

The original `from` address in `email.py` was derived from `FRONTEND_URL`:

```python
"from": f"{settings.app_name} <noreply@{settings.frontend_url.split('//')[-1]}>",
```

Which produced `noreply@pulse-frontend-navy.vercel.app`. Resend rejects this
because we don't own `vercel.app`. Switched the default sender to Resend's
sandbox (`onboarding@resend.dev`), which works without domain verification
but only delivers to the Resend account owner's email. Fine for testing.

Added `RESEND_FROM_EMAIL` env override so once a real domain is verified,
the production sender can be configured:

```bash
RESEND_FROM_EMAIL=noreply@pulse.example.com
```

## Jira workspace badge on cards

The user pointed out that feature cards on Changelog / Deprecated / Alert
panels showed product group + team + status badges but **never said which
Jira workspace the feature came from**. Once you have multiple workspaces
connected, this is critical context.

Added `jira_account_id`, `jira_account_label`, and `jira_base_url` to
`FeatureOut`. Built a small per-request lookup map so it's not an N+1 JOIN:

```python
async def _account_lookup(db, organization_id):
    rows = (await db.execute(
        select(JiraAccount).where(JiraAccount.organization_id == organization_id)
    )).scalars().all()
    return {r.id: (r.label, r.base_url) for r in rows}
```

Frontend got a soft blue `@ Default` badge next to the existing ones on
every feature card.

Initially also tried to make the ticket key clickable (deep-link to
`<jira_base_url>/browse/<ticket_key>`), but the user said:

> "I didn't mean to provide a link, just give info like where it came from"

Reverted the link. Kept just the badge.

## Conversational chatbot rewrite

Pulse's chatbot answers were technically correct but felt like printed
forms:

> *There's an existing implementation. Here are the matches:*
> *- Stripe Payment Retry — Checkout team — WEBT-101*
> *- Subscription Failed Payment Recovery — Billing — WEBT-2*
> *Score: 0.74 — strong match.*

That's a report, not a conversation. Rewrote the system prompt with explicit
"sound like" guidance:

```
- Write in natural, flowing prose — like you're explaining something over
  a coffee, not filing a report. Whole sentences. A sense of voice.
- Use friendly openers when they fit naturally: "Yep, looks like…",
  "Quick one —", "Hmm, nothing jumps out…", "Funny you ask…"
- Vary how you start replies. No two answers should open the same way.
- Weave the facts into sentences instead of stacking them into rows.
  ✗ "Apple Pay One-Tap — Checkout team — WEBT-18"
  ✓ "There's Apple Pay One-Tap, built by the Checkout team back in
     WEBT-18 — active, still in use."
- Markdown tables, dense bullet lists, and headers are usually overkill.
- Don't quote similarity scores as numbers ("0.42"). Translate them into
  language: "a fairly strong match", "loosely related", "nothing close".
```

Same answer now becomes:

> *Yep, looks like the Checkout team already has this covered — they built
> Stripe Payment Retry with Exponential Backoff over in WEBT-101, which
> retries failed charges up to 5 times. There's also a related one from the
> Billing team specifically for subscriptions (WEBT-2). Both still active.*
>
> *Worth pinging the Checkout team before you start anything new on this.*

Night and day in feel. Same data.

## Haiku for the query agent

The conversational answers were lovely but **slow**. Each query was
~10-15 seconds because the agent loop made 2-3 Claude calls back-to-back
on Sonnet. The total felt unbearable for a chatbot.

Switched `CLAUDE_QUERY_MODEL` from `claude-sonnet-4-6` to
`claude-haiku-4-5-20251001`. Heavy agents (duplicate, deprecation,
documentation) still use Opus where reasoning quality matters more than
latency.

Before:
- Sonnet: 10-15s per response

After:
- Haiku: 3-5s per response

3-5× speedup, no perceptible quality drop for Q&A.

## Streaming chatbot responses

This was the biggest single UX win of the day.

Before: user types question → spinner for ~3-5 seconds → entire answer
appears at once. Feels slow.

After: user types question → "Pulse is thinking…" for ~1s while tools run
→ first word appears → answer streams in word by word like ChatGPT. Same
total time, but the perception is dramatically faster because something
visibly happens almost immediately.

### Backend: SSE endpoint

Added a `run_agent_stream()` variant in `claude_client.py` using the
Anthropic SDK's streaming context:

```python
async with client.messages.stream(
    model=effective_model, max_tokens=1024,
    system=[...], tools=anthropic_tools, messages=messages,
) as stream:
    async for event in stream:
        if event.type == "content_block_delta" and event.delta.type == "text_delta":
            yield {"type": "text", "delta": event.delta.text}
    final_msg = await stream.get_final_message()

if final_msg.stop_reason != "tool_use":
    break
# else: process tool_use blocks, loop again
```

Wrapped in a FastAPI endpoint that emits Server-Sent Events:

```python
@router.post("/ask/stream")
async def ask_stream(body, current_user):
    async def event_source():
        async for event in query_agent.run_stream(body.message, ...):
            yield f"data: {json.dumps(event)}\n\n"
    return StreamingResponse(
        event_source(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

The `X-Accel-Buffering: no` header tells Railway's edge proxy not to buffer
the response — without it, all events would arrive at the client at the
same time, defeating the point.

### Frontend: ReadableStream → React state

`api.askStream(message, onEvent)` reads the stream via fetch's
`ReadableStream`:

```typescript
const res = await fetch(`${API_BASE}/api/ask/stream`, { ... });
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const parts = buffer.split("\n\n");
  buffer = parts.pop() ?? "";
  for (const part of parts) {
    const line = part.split("\n").find(l => l.startsWith("data: "));
    if (line) onEvent(JSON.parse(line.slice(6)));
  }
}
```

`SearchPanel` pre-creates an empty assistant turn and appends each text
delta to its content. The "Pulse is thinking…" indicator shows only while
the latest assistant turn has empty content — disappears the instant the
first token arrives.

The result: response feels ~5× faster than it actually is. This is the
moment Pulse went from "AI features bolted onto a dashboard" to "an AI
product." Genuinely satisfying to use.

## JiraAccount label uniqueness — per-org

User tried to add a Jira account labeled "Mozilor" in their new Mozilor
workspace. Got a 409 conflict, because the existing acme.com workspace
already had a "Mozilor" Jira account (a leftover from migration testing).

Looked at the model:

```python
label: Mapped[str] = mapped_column(String(128), unique=True, index=True)
```

That's a **global** unique constraint. Wrong for multi-tenant SaaS — two
different orgs should each be able to have a Jira account called "Mozilor"
without colliding.

Schema migration on Supabase:

```sql
ALTER TABLE jira_accounts DROP CONSTRAINT jira_accounts_label_key;
DROP INDEX ix_jira_accounts_label;
CREATE INDEX ix_jira_accounts_label ON jira_accounts(label);
ALTER TABLE jira_accounts ADD CONSTRAINT ux_jira_accounts_org_label
    UNIQUE (organization_id, label);
```

Updated the model `__table_args__` to declare the composite uniqueness, and
fixed `_label_in_use()` in the service to scope its check by
`organization_id`. Now identical labels across different orgs work
correctly; duplicates within the same org are still blocked with a clear
message.

## "The error message is just '409'"

User screenshot showed a banner with literally `409` as the error text.
That's because the generic frontend `http()` helper was throwing
`new Error("${res.status} ${res.statusText}")` and ignoring FastAPI's
`{detail: "..."}` response body.

Fixed `http()`:

```typescript
if (!res.ok) {
  let message = `${res.status} ${res.statusText}`;
  try {
    const body = await res.json();
    if (typeof body?.detail === "string") {
      message = body.detail;
    } else if (Array.isArray(body?.detail) && body.detail[0]?.msg) {
      message = body.detail.map(d => d.msg).join("; ");
    }
  } catch { /* fall through */ }
  throw new Error(message);
}

```

And restyled the JiraAccounts error banner with a leading ⚠ icon and a
dismiss × button.

Now: `label 'Mozilor' is already used by another account in this workspace`
instead of `409`. Same fix applies to every endpoint that uses `http()`.

## Reflections

**Deployment is mostly tactical mistakes.** The Railway flow itself is
beautiful — connect GitHub, click deploy, done. But every single small
operational gotcha cost real time: forgetting which service needs which
env var, Vercel's cache hiding env-var changes, the procrastinate kwargs
signature, the session-pooler connection cap. None of these were
architecture decisions; all of them were "this small detail wasn't
documented in the way I read it." The 5-hour debugging sessions of 2015
have been compressed to 30 minutes today, but they still exist.

**Streaming is the threshold for "feels like AI."** Before today's
streaming work, Pulse felt like a Postgres app that happened to use
Claude. After streaming, it feels like an AI product. Same model, same
data, same answers. Just the timing of when characters appear changed.
That's a remarkable thing about LLM UX — perception of intelligence is
deeply tied to perception of immediacy.

**Multi-tenancy is never "done."** Yesterday's audit found 3 bugs that
would have leaked data across orgs. Today found another (the global
`label` unique constraint that prevented multi-tenant Jira accounts).
Every "is this thing actually per-tenant?" question I'd ever forgotten
to ask manifested as a real bug eventually. The discipline is to keep
finding them before customers do.

**Conversational tone is a 50-line system prompt change.** The chatbot
went from feeling like Stack Overflow search to feeling like a colleague.
No model swap, no architecture change. Just an honest description of how
I wanted it to sound, with concrete examples of what to do and not do.
The prompt was longer than the diff most days. Worth re-reading the
"WHAT TO SOUND LIKE" section any time the tone drifts.

Tomorrow: probably a quieter day. Resend domain verification, maybe
custom domain, maybe Sentry. Pulse is now genuinely runnable as a
product, which is the threshold I've been chasing since Monday.
