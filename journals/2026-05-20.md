# Pulse — Dev Journal · 2026-05-20

A long, productive day. We took Pulse from "works for a small team on SQLite"
to "genuinely multi-tenant, multi-user, production-shaped." Eight distinct
threads of work landed in tree, in this order:

1. Public sign-up flow + Login UI
2. Project classifier rewrite (LLM-driven → deterministic)
3. Cascade-on-rename for product groups
4. Auto-sync of Jira projects (background + manual + delete-on-Jira-deletion)
5. Chatbot transparency for historical (project-deleted) product groups
6. Multi-account Jira — Phases 1, 2, 3
7. SQLite → Postgres migration with full data preservation
8. Production hardening — optimistic concurrency + Arq job queue

Below is the play-by-play, with the reasoning behind each decision and the
bugs we hit along the way.

---

## Morning — User-facing fixes

### Sign-up flow

The product was admin-only by design — only the seeded `.env` admin could
log in, and a separate `/auth/register` endpoint required admin auth. For
"real product" use we needed self-service.

Shipped `POST /auth/signup` (public, non-admin by default) plus a Login
toggle. Tokens go straight to JWT; password ≥ 8 chars enforced both client
and server side. Admin registration via `/auth/register` stays — that's how
you grant admin to specific users.

> **Note**: every signup hits the same `users` table; passwords bcrypt-hashed.
> Login still authenticates against DB rows — `.env` is only used to seed the
> *first* admin, not as a live credential source.

### The classifier bug — "CookieEat → CookieYes"

User reported: created a new Jira project "CookieEat" → Pulse auto-bucketed
it into the existing "CookieYes" product group. Added a feature in CookieEat
→ it landed under CookieYes. Asked the chatbot about CookieEat → "doesn't
exist, did you mean CookieYes?"

Three layered bugs from one root cause:

1. **Classifier**: the LLM prompt said "prefer an existing group when there's
   an obvious match." Claude latched on `Cookie` substring and picked
   `CookieYes`. Substring is not brand identity.
2. **Tool schema**: `store_feature` and `list_features` had
   `enum: ["CookieYes", "WebToffee", "WebYes"]` baked in. Even if the project
   were correctly classified, Claude *couldn't* pass `CookieEat` through.
3. **Chatbot prompt**: hardcoded the same three groups. So even with correct
   data, the chatbot would refuse to look up CookieEat.

**Fix:**

- Removed the LLM from classification entirely. Replaced with
  deterministic word-boundary matching: reuse only when one group name is a
  leading word of the other (e.g. "CookieYes Mobile" → "CookieYes" passes,
  "CookieEat" → "CookieYes" does NOT).
- Dropped enum constraints from tool schemas.
- Made chatbot prompt list the live `_existing_product_groups()` dynamically.

> **Lesson:** when the LLM is asked a fuzzy classification question with a
> tempting wrong answer in the set, it will pick the wrong answer. Substring
> overlap is the LLM's catnip. Deterministic rules win for product taxonomy.

### Cascade on product-group changes

Before: editing a project's product_group only updated the `projects` row.
Stale data everywhere else — old features still tagged with the old group,
vector store still indexed under the old label.

Now `set_product_group()` walks every `Ticket` (by `project == key`) and
every `Feature` (by `ticket_key LIKE '{key}-%'`), updates the column, AND
re-upserts the feature into the vector store with corrected metadata. The
chatbot, search, and filters all stay consistent.

Also added `reclassify_inferred_projects()` on startup — for every project
still marked `is_inferred=True`, re-run the new classifier and cascade-fix
any that change. Self-healing for existing data.

## Mid-morning — Jira project lifecycle

User asked: "if I create a new project in Jira, when does it show up in
Pulse?" Pre-fix, the answer was "the first time a webhook fires for it."
That's bad UX — they wanted projects visible in the UI as soon as they
existed in Jira.

Shipped three triggers, all calling the same `sync_from_jira()`:

1. **Startup** — once at boot.
2. **Background poll** — every 120 seconds (configurable via
   `JIRA_PROJECT_SYNC_INTERVAL_SECONDS`).
3. **Manual button** — "Sync from Jira" in the UI for instant refresh.

Then user said: "I deleted a project in Jira, it's still in Pulse." Added
delete-mirroring: after a *successful full traversal* of Jira's project
list, anything in Pulse not in Jira's response is removed. Guarded against
partial fetches so a transient network blip doesn't wipe the registry.

Then we briefly added a manual Delete button per project — user pushed back:
"deletion should be driven by Jira state, not human clicks." We pulled the
button. The deletion logic stayed (internal-only), but the UI is now fully
Jira-state-driven.

### Features survive deleted projects

Subtle design decision: deleting a project also deletes its cached `Ticket`
rows but PRESERVES `Feature` rows. Reasoning: a Feature represents
organizational memory — work that was done, knowledge worth keeping — even
if the originating Jira project is gone.

This led to a chatbot complaint: "WebHi was deleted, but its features are
in the DB. Why can't the chatbot find them?" Because `_existing_product_groups()`
was sourcing from the `projects` table only.

**Fix:** unioned in `features.product_group` too. Then made the chatbot
prompt label these as `(historical)` so it can say "WebHi's project was
removed but here's what we built under it."

> **Lesson:** when you choose to preserve data after a deletion, you have to
> update every downstream "known things" query to recognize the preserved
> shape. The graveyard counts as a place to look.

## Afternoon — Multi-account Jira (the big one)

User's situation: one Atlassian workspace today, planning for multiple
later. Asked "how do we make this multi-account?"

Honest framing back: it's a real refactor, not a flag flip. Touch schema,
service layer, UI, webhook routing, and migration. Broke it into 3 phases.

### Phase 1 — Schema + service layer

New `JiraAccount` model: `id, label, base_url, email, api_token (Fernet
encrypted), webhook_secret, is_active, is_default`. Nullable `jira_account_id`
FK columns added to `Project`, `Ticket`, `Feature` via additive migration.

Cascade rules:

- Account → Project: CASCADE (delete account, projects go with it)
- Account → Ticket: CASCADE (same — they're a cache)
- Account → Feature: **SET NULL** (preserves org memory; matches the
  "features outlive projects" principle from earlier)

Tokens encrypted with `cryptography.fernet`. Key sourced from
`PULSE_ENCRYPTION_KEY` env var, or auto-generated to `.pulse_encryption_key`
(gitignored) co-located with the SQLite DB.

First-boot bootstrap: if `.env` has the legacy single-account JIRA_*
variables and no `JiraAccount` row exists, create the default account from
those values and backfill all existing rows' `jira_account_id`. Idempotent
on subsequent boots.

Decision deferred: kept `Project.key` as PK. Two accounts sharing the same
project key would collide on insert. Documented as "Phase 1.5 when a second
workspace is actually added." Avoided the SQLite table-recreation pain for
now.

### SQLite → Postgres migration

After Phase 1 was clean, user wanted the production swap.

Wrote `backend/migrate_sqlite_to_postgres.py`. Reads source SQLite,
verifies target Postgres is empty (safety guard), creates schema via
`Base.metadata.create_all`, then bulk-copies each table in FK-safe order
(`users → jira_accounts → projects → tickets → features → alerts →
processed_events → agent_runs`), preserving every primary key. Resets
Postgres sequences so future inserts don't collide.

First run got 6 of 8 tables in before:

```
asyncpg.exceptions.DataError: invalid input for query argument $4
... value out of int32 range  (value: 1779086776320)
```

`processed_events.payload_timestamp` was declared `Integer` in the model.
SQLite stores integers in 64-bit cells regardless of declared width and
silently accepted Jira's millisecond timestamps. Postgres enforces `INT4`
(32-bit ceiling: ~2.1B) and rejected anything larger.

**Fix:** changed the model to `BigInteger`. Dropped and recreated the
target database. Re-ran migration — clean: **520 rows across 8 tables**.
Then flipped `DATABASE_URL` in `.env` and restarted.

> **Lesson:** the reason to migrate to Postgres isn't just scale — it's
> *correctness*. SQLite's permissive typing was hiding a real type-width
> bug that would've bitten us eventually. Strict databases force honest
> schemas. Worth doing even if your workload doesn't demand it yet.

### Phase 2 — Admin UI

Backend: `JiraAccountOut/Create/Update/TestResult` schemas. CRUD routes
under `/api/jira-accounts`, all gated by `Depends(get_current_admin)`.
Tokens NEVER returned over the API — `JiraAccountOut` only exposes
`has_token: bool` / `has_webhook_secret: bool`.

Service-layer guarantees:

- Label uniqueness enforced.
- Non-empty webhook secrets must be unique across accounts.
- Only ONE account can be `is_default=True` at a time — set on one auto-clears others.
- Cannot delete the last remaining account (breaks webhook fallback).
- Cannot un-set the only default (same reason).
- Updates invalidate the cached httpx client so new credentials are picked up immediately.

Frontend: new "Jira Accounts" sidebar tab (admin-only — filtered out for
non-admins). Each card shows badges (default / active / token ✓ / secret ✓),
a "Test" button that pings `/rest/api/3/myself`, and inline Edit/Delete.
Edit-mode: leaving the token field blank means "keep existing" — only fill
it when rotating. Same for webhook secret. This matters because the API
never returns the value, so the UI can't pre-populate.

Also added an `@ <account-label>` badge to each project card on the
existing Jira & Agents tab. Denormalized via `jira_account_label` in
`ProjectOut` so non-admins can see it without needing the admin-only
accounts endpoint.

> **Lesson:** "write-only" fields (passwords, tokens, secrets) need a UX
> convention. The "blank = keep existing" pattern is widely understood and
> matches how every credential-rotation UI does it. Don't try to be clever.

### Phase 3 — Per-account webhook routing

Pre-fix, the webhook URL was singular: `POST /jira/webhook?token=<secret>`
and the server reverse-looked-up which account the secret belonged to.
Works, but fragile — two accounts must never share a secret, and a leaked
secret has no second factor.

Shipped two routes sharing one handler:

```
POST /jira-webhook/{account_id}?token=<secret>   (preferred)
POST /jira/webhook?token=<secret>                (legacy alias)
```

The per-account URL validates BOTH the path account_id AND the token —
defense in depth. The legacy route stays so existing Jira webhook configs
don't break overnight.

Idempotency hash now incorporates `account_id` so two workspaces firing
identical logical events on identically-keyed tickets dedupe independently.

Added a "Webhook URL: ... [Copy]" row to each account card in the admin UI.
Tells users exactly what to paste into Jira's webhook config. Uses
`PULSE_PUBLIC_BASE_URL` from `.env` (e.g. ngrok URL) to render the full URL;
falls back to path-only with a tip if unset.

Found and fixed an old paper cut on the way: webhook handler was 500'ing
on empty/malformed JSON bodies. Now returns a clean 400 with the error
message. (Discovered when zsh ate a `-d` flag during our curl tests.)

> **Lesson:** every endpoint that does `await request.json()` needs an
> explicit try/except — Starlette doesn't translate JSONDecodeError into a
> 400 automatically. This is the kind of thing that only shows up when
> someone runs an experimental curl.

## Evening — Production hardening

User pulled the morning's "what's needed for multi-user" list back out and
asked me to verify which items shipped. Three of four were done (Postgres,
auth, multi-account). Two were open:

- **Optimistic concurrency** on `mark_feature_deprecated` (rare race that
  could clobber `restored_at`)
- **Real job queue** instead of FastAPI `BackgroundTasks`

User said: "do both — I'm building a real product."

### #3 — Optimistic concurrency

Replaced the ORM read-then-mutate pattern with a conditional UPDATE:

```python
result = await db.execute(
    sqla_update(Feature)
    .where(Feature.id == feature_id, Feature.status == original_status)
    .values(status="deprecated", deprecation_reason=reason, restored_at=None, restored_reason=None)
)
if (result.rowcount or 0) == 0:
    return {"error": "concurrent_modification", ...}
```

If the row changed under us between read and write, the UPDATE matches 0
rows and we surface `concurrent_modification` cleanly. Same pattern on the
restore endpoint, except it raises HTTP 409 instead of returning a tool
error.

Also added an "already deprecated" idempotent-success short-circuit so
duplicate webhooks don't churn through the UPDATE machinery for nothing.

### #4 — Arq job queue + Redis

Picked Arq over Celery. Reasoning:

- Pulse is async top-to-bottom (FastAPI, async SQLAlchemy, async httpx,
  async Anthropic SDK). Celery's sync core would force bridging.
- Arq is async-native, simple, used in production by the Pydantic maintainer.
- Redis broker is one Docker command. No RabbitMQ overhead.

Architecture:

```
POST /jira-webhook/{id}     ──► dispatch_event()
                                    │
                                    ├── Arq pool ──► Redis ──► Worker process
                                    │                             │
                                    │                             ▼
                                    │                       orchestrator.handle_event()
                                    │
                                    └── (fallback) BackgroundTasks
```

`app/services/dispatcher.py` is the single decision point — webhook
handlers call `dispatch_event()` and don't care which backend is wired.
`app/worker.py` defines the Arq Worker. Workers share the same code,
`.env`, encryption key, and database as the API process.

Graceful degradation: if `REDIS_URL` is unset OR the pool fails to connect,
we log a warning and fall back to `BackgroundTasks`. Dev workflow unchanged
when Redis isn't running. Prod sets `REDIS_URL` and starts the worker.

Retry policy: 5 tries with exponential backoff (Arq default). 300-second
job timeout. Finished jobs kept in Redis for 24 hours so you can inspect
outcomes.

`/api/status` now exposes `queue_mode: "arq" | "background_tasks"` so admins
can see at a glance which path is wired up. Webhook responses include
`dispatch: {mode, job_id}` so you can trace any single event to its job.

> **Lesson:** make the production dispatch path the default, but degrade
> gracefully to a simpler one in dev. Forcing developers to run Redis just
> to test a webhook would have been hostile. The dispatcher abstraction —
> one function call, two backends — kept the webhook handler clean.

## Reflections

Today felt like four sessions stacked into one. The connective tissue: each
change exposed the next problem. Fix the classifier → discover the cascade
is missing. Add the cascade → realize the chatbot needs to know about
historical groups. Make it multi-account → realize SQLite has been hiding a
type-width bug. Each fix made the next gap visible.

A few things that worked particularly well:

1. **Phasing the multi-account refactor** (1: schema, 2: UI, 3: routing).
   If we'd tried to ship it as one PR we'd have lost an afternoon to a single
   merge conflict. Each phase landed independently and could be verified
   before the next started.

2. **Deterministic over LLM-driven for classification.** The LLM had been
   wrong in a sneaky way (over-merging on substring) and replacing it with
   word-boundary matching made the behavior predictable, debuggable, and
   testable. The LLM is back to doing what it's good at (reasoning over
   unstructured text), not what it's bad at (categorical decisions where the
   wrong answer is enticing).

3. **Graceful degradation as a design principle.** Both Phase 3 (legacy
   `/jira/webhook` URL still works) and the Arq dispatcher (BackgroundTasks
   fallback) kept dev workflows unblocked while shipping production paths.
   You don't have to break the easy case to support the hard one.

4. **Optimistic concurrency over locking.** The conditional UPDATE pattern
   is one line of code and zero infrastructure. It would have been very
   tempting to reach for SELECT FOR UPDATE or a Redis lock. Neither was
   needed.

A few things to revisit:

- **`Project.key` as PK is a Phase-1.5 time bomb.** It'll bite the first
  time a second workspace registers a project with a key that already
  exists. The fix (composite UNIQUE constraint with a synthetic `id` PK)
  is well-understood — it's the SQLite table recreation pain we deferred.
  Owe it before adding a second real workspace.

- **No tests yet.** Every fix today was verified by running `uvicorn` and
  exercising the feature manually (or via curl). For "real product" this is
  the next thing to address — at minimum a smoke suite covering the
  classifier, the cascade, multi-account isolation, and webhook routing.
  A handful of pytest-asyncio tests would have caught most of today's bugs
  before they hit the user.

- **Worker observability is thin.** Arq logs to stdout but there's no
  dashboard. Long term, expose queue depth + retry counts in `/api/status`
  or build a small admin page. For now, `redis-cli LLEN arq:queue` is the
  fallback.

Net: Pulse went from "demo-quality single-tenant" to "deployable multi-tenant
with durable async dispatch and encrypted credentials" in a single day. The
foundation is now solid enough to invite a second customer onto it.
