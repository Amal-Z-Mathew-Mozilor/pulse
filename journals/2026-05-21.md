## Morning — Frontend deployment polish

Yesterday we pushed the frontend to GitHub and Vercel did a first build. Today
spent the first hour cleaning up the bumps from that.

### TypeScript build errors

Vercel's first build failed with two errors:

1. `Property 'env' does not exist on type 'ImportMeta'` — Vite's `import.meta.env`
   types weren't included. Fix: added `"types": ["vite/client"]` to
   `tsconfig.json`.
2. `Type '...' is not assignable to type 'HeadersInit'` — I'd done a conditional
   spread `{ ...(API_BASE ? {"ngrok-skip-browser-warning": "true"} : {}) }`
   which TS couldn't narrow. Replaced with a typed `Record<string, string>`
   that's mutated conditionally.

After fix → build clean.

### "Backend status unavailable" — hardcoded path bug

App opened on Vercel, login worked, but the status banner showed "Pulse can't
reach localhost:8000". Turns out `App.tsx` had its own `fetch("/api/status")`
call that bypassed `api.ts` entirely and used a hardcoded relative path. On
Vercel that resolves to `vercel.app/api/status` (nothing there).

Fix: route the status fetch through `API_BASE` like every other call, and
update the error message to show the actual URL being attempted instead of
the misleading "localhost:8000" string.

### ngrok browser-warning interstitial

Free-tier ngrok shows an HTML "you're visiting an ngrok tunnel" page on the
first call from a new IP. Our JSON-fetching frontend just saw HTML and crashed.

Fix: send `ngrok-skip-browser-warning: true` header on every API call when
`VITE_API_BASE_URL` is set. The header is documented by ngrok specifically
for this case.

## Multi-tenancy — the big architectural turn

The user wanted to give Pulse to multiple customers. With everything in shared
tables, Customer A would see Customer B's features. We had to add an
`Organization` model and scope every query.

### Clarifying what "tenant" means here

Spent some time on the conceptual model. Pulse's value is *cross-workspace*
visibility — within one company, Pulse should see all their Jira workspaces
together. So:

  - tenant = company (an `Organization` row)
  - within a tenant: all Jira workspaces visible to all that org's users
  - across tenants: complete isolation

That's the textbook B2B multi-tenant pattern. Don't confuse "isolating
workspaces" (bad, kills the product) with "isolating companies" (essential).

### Schema changes

Added two new tables:

- `organizations` — `id`, `name`, `domain` (unique), `created_at`
- `email_verifications` — token, user_id (FK), expires_at, used (single-use)

And `organization_id` (nullable FK → organizations) on every row-bearing
table: users, jira_accounts, projects, tickets, features, alerts, agent_runs.
ProcessedEvent intentionally left out — webhook dedup is org-agnostic.

`User` also got `email_verified BOOLEAN` and (later) `google_id VARCHAR`.

### Application-layer enforcement

Every list endpoint now does:

```python
.where(Feature.organization_id == current_user.organization_id)
```

And every detail endpoint (restore feature, mark alert read, delete jira
account, etc.) first checks `feature.organization_id == user.organization_id`
before doing anything — returning 403 if mismatched. For vector search we
pass the org_id through a `ContextVar` so the tool handler can include it
in the Pinecone (later pgvector) filter.

The same `organization_id` flows webhook → orchestrator → tool calls → DB
writes, stamped at every step. We later found 3 places where it *wasn't*
flowing properly (see audit below).

### Domain matching for signup

Decided: first user from a domain creates the org and becomes admin;
subsequent users from the same domain auto-join. Generic email domains
(gmail, yahoo, outlook, etc.) are rejected entirely — Pulse is for company
work emails only.

This collapses the "invite link vs auto-join vs approval" UX into a single
pleasant flow:

```
alice@mozilor.com signs up first    → org "Mozilor" created, alice = admin
bob@mozilor.com signs up next       → joins "Mozilor" as regular user
hacker@gmail.com signs up           → blocked with clear message
```

Later in the day we added explicit `mode: "create" | "join"` to the signup
endpoint so the UI can show two distinct flows, with the backend rejecting:
- `mode=create` against a domain that already has an org → 409
- `mode=join` against a domain with no existing org → 404

Much clearer than the implicit version.

### Email verification

Generated `secrets.token_urlsafe(32)` per signup, stored in
`email_verifications` with a 24h expiry. Endpoint `GET /auth/verify?token=...`
flips the user's `email_verified=true` and returns a JWT.

Login endpoint now rejects unverified users with a 403 "Please verify your
email first" — same error whether the password is wrong or the email isn't
verified, to avoid leaking which problem it is to attackers.

For email sending, the design: if `RESEND_API_KEY` is set in env, send via
Resend's HTTP API. If not, log the verification link to stdout so dev still
works. Same shape later for password reset emails.

### Password reset

Same pattern: `PasswordReset` table, `POST /auth/forgot-password`,
`POST /auth/reset-password`. Two security touches worth keeping:

  1. `/auth/forgot-password` returns the **same** generic success message
     regardless of whether the email exists. Otherwise an attacker can probe
     which emails are registered.
  2. Issuing a new reset token invalidates all prior unused tokens for that
     user — `UPDATE password_resets SET used=true WHERE user_id=$1 AND used=false`.
     Stops the "user forgot password three times" race where an old link
     still works.

### Login by username OR email

Trivial change — the existing `authenticate_user(username, password)` got
renamed to `authenticate_user(identifier, password)` and now first checks if
the identifier contains `@`. If yes, look up by email; otherwise by username.
Frontend label became "Username or Email".

## Google OAuth — the rabbit hole

Wanted "Continue with Google" buttons everywhere. Picked the implementation
that uses Google Identity Services via the official `@react-oauth/google`
React library.

First implementation used the `<GoogleLogin>` component (rendered by Google
inside an iframe). Worked, but looked terrible — Google's official button has
a white circle around the G logo on a black background that clashes with our
dark UI. No CSS in the world fixes that (it's inside their iframe).

Switched to `useGoogleLogin` hook which returns an OAuth `access_token` from
a custom button. The cost: backend `/auth/google` now has to call Google's
userinfo endpoint to verify the token and get email/sub. Same security
guarantees, full control over button design.

Final custom button:
- Dark `panel-2` background matching the form inputs
- Real multi-color Google "G" SVG, no white box
- Soft blue glow on hover, matching the gradient Sign in button

Backend supports both `access_token` (custom button) and `credential` (legacy
ID-token flow) — same endpoint, dispatches based on which field is set.

### Domain rules apply to Google too

Same gating: a Gmail-account sign-in is blocked with "Please use your work
email". Whatever domain Google says the email belongs to gets routed through
the same auto-create-or-join org logic. If a Google sign-in matches an existing
password user by email, we link them by setting `google_id` on the existing
user.

## Multi-tenancy isolation audit

Before declaring multi-tenancy "done," I wrote an automated test that mints
JWTs for users in different orgs and probes 17 endpoints/scenarios for
cross-org leaks. The plan:

- 3 orgs (acme, mozilor, gmail)
- Insert a Mozilor-only test feature into the DB + vector store
- Try every listing endpoint, every direct-ID endpoint, the chatbot, raw
  semantic search, and agent runs — both as the "right" user and the "wrong"
  user from another org

Result: **16/17 passed**, and the one "fail" was a false positive in the
test itself (my regex checking if the response text contained the feature's
name didn't account for the user's own query containing the name).

But the test DID find 3 real bugs hiding under the surface — places where
`organization_id` wasn't propagating end-to-end through the webhook pipeline:

### Bug 1 — webhook didn't stamp `organization_id` on the event

`routes/webhooks.py` was setting `event["jira_account_id"]` before calling
`dispatch_event(...)`, but not `event["organization_id"]`. The orchestrator
read it from the event and got `None`. Fix: also stamp
`event["organization_id"] = account.organization_id`.

### Bug 2 — orchestrator didn't pass org_id to `get_or_register`

When a brand-new Jira project fires its first webhook,
`project_registry.get_or_register(key)` auto-registers it. The function
*accepts* an `organization_id` kwarg, but the orchestrator wasn't passing it.
So the new Project row landed with `organization_id = NULL`. Fix: pass it
through.

### Bug 3 — `upsert_ticket` ignored `organization_id`

The orchestrator was passing `organization_id` in the payload dict to
`jira_client.upsert_ticket(payload)`, but `upsert_ticket` only read
`jira_account_id` off the dict, never `organization_id`. So Tickets landed
with NULL org. Fix: check for and assign `organization_id` in upsert_ticket.

### Defensive fallback

Even after fixing 1-3, I added a guard in the orchestrator: if
`event["organization_id"]` is missing for any reason, look it up via the
JiraAccount row. Belt-and-suspenders so we never silently create un-scoped
rows again.

After fixes, re-ran the synthetic-webhook test end-to-end: Ticket + Project
both correctly carry `organization_id`, all 17 isolation probes pass.

> The lesson: multi-tenancy isn't done when you've added `organization_id`
> columns. It's done when every code path that *creates* a row also *sets*
> that column, and you've tested every path. Easy to miss one.

## Supabase migration

The user wanted to deploy. Step one: get the database off the Mac.

### Why Supabase over Neon

Quick comparison ended with Supabase winning on the free tier specifically
because:
- Neon's free tier limits **compute hours** to 100/month. With an always-on
  backend that keeps the connection pool warm, you'd burn through it in
  ~4 days.
- Supabase has unlimited compute time on free tier, but **pauses the project
  after 7 days of no traffic**. Fine for an actively-used app.
- Supabase's SQL editor is genuinely nice for debugging multi-tenant data.

### Project creation gotcha — disable Data API

Supabase enables a REST API for every table by default. If you leave it on
without enabling Row Level Security, *anyone with the anon key reads everything*.
Since we use our own backend with SQLAlchemy (never the auto-REST API), I
told the user to **uncheck "Enable Data API"** during project creation. That
makes the RLS security warnings later in the Advisors page irrelevant — there
is no public endpoint to those tables.

### Connection pooling — Session vs Transaction

Supabase exposes 3 connection modes:
- **Direct** (port 5432, IPv6 only) — won't work from Railway (IPv4)
- **Transaction pooler** (port 6543, IPv4) — best perf, but breaks
  prepared statements *and* LISTEN/NOTIFY
- **Session pooler** (port 5432 via pooler, IPv4) — slightly slower but
  full feature parity

Tried transaction pooler first. asyncpg complained about prepared statements
(known PgBouncer transaction-mode issue, fixable with `statement_cache_size=0`).
Worked. But later, when adding procrastinate, hit the LISTEN/NOTIFY ceiling —
transaction mode multiplexes connections per query, so a `LISTEN channel`
on one query may not see `NOTIFY channel` on another.

Switched everything to the **session pooler** (port 5432 via pooler URL).
All features work, removed the `statement_cache_size=0` workaround.

### The migration script

Wrote a one-shot Python script:

1. For each table, in FK-dependency order, `SELECT *` from local Postgres.
2. INSERT into Supabase with `ON CONFLICT DO NOTHING`.
3. Reset every sequence to `MAX(id) + 1` so future inserts don't collide.

Hit two bumps:

**JSON columns**: `components`, `raw_payload`, `comments`, etc. are stored as
JSON in Postgres. When I read them via SQLAlchemy text() queries, they came
back as Python lists/dicts. asyncpg couldn't encode them as text for the
INSERT into a JSON column. Fix: `json.dumps()` for any list/dict value.

**Failed-transaction rollback**: My first attempt wrapped the whole migration
in one transaction. When tickets failed (due to the JSON encoding bug above),
the entire transaction rolled back — including the orgs/users/jira_accounts
that had "succeeded". Made the next retry hit a different bug because the
parent rows weren't there. Fix: per-table commits so partial progress sticks.

Final run: **556 rows migrated** across 11 tables, in about 8 seconds.

## Pinecone → pgvector

Once everything was in Supabase, the user asked the right question: "Postgres
has pgvector, can we just put the vectors there and drop Pinecone?"

Yes. And `pgvector` is a Supabase-supported extension.

### The win

Before:
- Pinecone account, API key, separate "database"
- Multi-tenant filter via Pinecone metadata syntax (`{"organization_id": 3}`)
- Risk of feature row and vector drifting out of sync
- Hard limits on free tier

After:
```sql
ALTER TABLE features ADD COLUMN embedding vector(384);
CREATE INDEX features_embedding_idx ON features
USING hnsw (embedding vector_cosine_ops);
```

Now the multi-tenant search is just SQL:
```sql
SELECT *, (embedding <=> :query_vec) AS distance
FROM features
WHERE organization_id = :org_id AND status = 'active'
ORDER BY embedding <=> :query_vec
LIMIT 5;
```

The `<=>` operator is cosine distance. Multi-tenancy is enforced via the same
`WHERE` clause the rest of the app already uses — no special filter syntax
to forget. And the feature's row + vector live in the same DB transaction —
upsert is atomic.

### Implementation

Replaced `app/services/vector_store.py` entirely. New class `PgVectorStore`
uses `psycopg` (sync, since the existing interface is sync — the rest of the
code is async but the Pinecone client was also sync). Same public API: 
`upsert`, `upsert_text`, `query`, `query_text`, `delete`, `size`.

Wrote a backfill script that re-embedded all 27 existing features and
populated the new `embedding` column. Took 10 seconds.

Verification: ran the same `OAuth middleware` semantic search query both
before and after — same top hits, similar scores. pgvector returned:
```
0.715  Centralized OAuth2 Auth Middleware
0.678  OAuth Middleware with Token Rotation
0.593  Google OAuth Customer Login
```

Cross-org search test: mozilor user searched same query → 0 results. The
SQL `WHERE organization_id = ?` does its job.

### Scale check before committing

Pinecone is faster than pgvector at huge scale (10M+ vectors). Pulse stores
one vector per feature. Even a hypothetical customer with 50,000 features
(absurd for an org-memory tool) is well within pgvector's HNSW index sweet
spot (~10-20ms queries). So we're not giving up anything realistic.

## Redis → procrastinate

Right after that, the user asked the *next* right question: "we only track
Jira tickets, why do we need a queue at all?"

That triggered a good architectural discussion. The queue isn't because Jira
data is special — it's because:

- Jira webhooks must respond within ~10 seconds (otherwise Jira retries)
- A single agent run takes 15-30 seconds (multiple Claude calls)
- So we have to ACK the webhook fast and process the work asynchronously

Three levels of "async processing":
1. **FastAPI BackgroundTasks** — fire-and-forget within the API process. No
   infra. No retries. Events lost on restart.
2. **In-process queue with retries** — better, still in the API process.
3. **External queue (Arq+Redis or procrastinate+Postgres)** — durable,
   retries, multiple workers, observability.

For Pulse's current scale, level 1 is genuinely fine. The user wanted level
3's guarantees but without Redis. That's exactly what procrastinate does —
Postgres-backed queue, identical guarantees to Arq+Redis (durability, retry
with backoff, parallel workers).

### How procrastinate works under the hood

1. **Defer** = INSERT into `procrastinate_jobs` table + `NOTIFY`
2. **Worker** = a long-running process that's `LISTEN`ing on the channel
3. When NOTIFY fires, worker grabs the next job via
   `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` (atomic claim, multi-worker safe)
4. Run the job. On success → mark `succeeded`. On exception → re-queue with
   exponential backoff up to N attempts.

That's the entire algorithm. ~5ms pickup latency thanks to LISTEN/NOTIFY
instead of polling.

### The migration

Replaced `app/worker.py` and `app/services/dispatcher.py`. About 80 lines
changed total — the public interface is nearly identical to Arq:

```python
# Before (Arq)
job = await pool.enqueue_job("handle_event", event)

# After (procrastinate)
job_id = await handle_event.defer_async(event=event)
```

Then applied the procrastinate schema to Supabase (4 tables + a bunch of
stored procedures, applied via `await app.schema_manager.apply_schema_async()`).

End-to-end webhook test: fired a synthetic webhook, watched the procrastinate
worker pick it up via LISTEN/NOTIFY ~5ms later, run the orchestrator, write
the Ticket with the correct `organization_id`. ✅

Cleanup: removed `arq` and `redis` from `requirements.txt`, uninstalled both
packages, removed `REDIS_URL` from `.env`, removed Pinecone env vars too.

### One CLI gotcha

The `procrastinate` CLI's `--app=app.worker.app` argument couldn't find the
module on first try — the CLI doesn't add CWD to `sys.path`. Solved with
`PYTHONPATH=. procrastinate --app=app.worker.app worker`. Both `Procfile`
and Railway's start command for the worker use this prefix.

## Railway deployment

By 5pm we had:
- Backend code working locally against Supabase
- All env vars known
- All external services consolidated to one Postgres

Time to put the backend on Railway.

### Repo setup

The user has the backend in a monorepo with the frontend (which is already
deployed separately). Initialized a fresh git repo inside `backend/`, made
sure `.gitignore` covered `.env`, `.pulse_encryption_key`, `.venv/`, and the
local `.db` files. Verified with `git diff --cached --name-only` that
nothing sensitive was staged. Pushed to a new GitHub repo
`Amal-Z-Mathew-Mozilor/pulse-backend`.

### Procfile

Defined two process types in `Procfile`:
```
web: uvicorn app.main:app --host 0.0.0.0 --port $PORT
worker: PYTHONPATH=. procrastinate --app=app.worker.app worker
```

Railway picks up the `web` process automatically. For the worker, you have
to manually add a second service from the same repo and set the custom start
command.

### Strong secrets

Generated a real JWT secret: `python -c "import secrets; print(secrets.token_hex(32))"`.
Reminded the user to back up `.pulse_encryption_key` — losing it makes every
stored Jira token unreadable. Both got pasted into Railway's Variables.

### Crash 1 — DATABASE_URL not set on web service

Web service crashed on first deploy with:
```
psycopg.ProgrammingError: missing "=" after "sqlite+aiosqlite:///./pulse.db"
```

The user had set env vars on the worker but not on web. Walked through
Railway's per-service variable model. Pasted the env var block into web.
Then noticed the worker had the same issue (env vars were on web but not
worker, then both got swapped — Railway sometimes confusingly toggles
between service-scoped and project-scoped vars). Set the same block on
both, both came online.

> **Lesson for next time**: use Railway's *Shared Variables* feature so
> env vars are defined once at project level and inherited by both services.
> Avoids the "I forgot to set X on the worker too" failure mode.
